# Project Overview

**Product goal**: build a decision workflow that helps users continuously improve their own trading decision model. This is not a trading terminal, not TradingView, not CoinGlass, not Bloomberg. The core asset is the Decision Weight Model, not market data — every trade is an experiment, and every experiment improves the user's decision model. (Source: `MVP Handbook.md`, `Quant Decision System.md` — both Frozen, both still authoritative for the product vision and the frozen 6-page core workflow; not duplicated here.)

**Current development phase**: past the original "mock-data-only prototype" stage named in `MVP Handbook.md`. **The full Research → AI → Strategy pipeline is now real and automatic** (Sprint 3.3C) — clicking "开始 AI 分析" on Research runs fresh data collection, image evidence parsing, Analysis Payload + Prompt Record creation, a real Main Analysis Model request (routed through the exact AI Connection configured for that role), automatic AI Response Parser validation, and — only once a valid `AIResponseRecord` exists — automatic navigation to a real Strategy page. No manual step is required; the dev-only Prompt Preview modal remains available for inspection/debugging but is no longer needed to complete an analysis. Settings manages multiple named AI Connections (Sprint 3.3B.2, `Settings → AI Connections`) with a separate Model Role layer (Main Analysis / Evidence Parser) pointing at whichever connection+model should do each job — the Main Analysis role is what the automatic flow now actually uses. Image Additional Evidence continues to be really parsed (Sprint 3.3B), including WHO appears to have posted a social-media screenshot (Sprint 3.3B.2), never a trading recommendation. Execution remains intentionally disconnected from real Strategy data (future sprint).

**High-level architecture**: one static frontend file (`prototype/index.html`, no bundler) talking to a local Node backend (`pipeline/`, no framework) over plain HTTP/JSON. See the pipeline below.

The Analysis Runner (Research's "开始 AI 分析") now automatically drives every arrow in this diagram in order: fresh collection → evidence parsing → Payload → Prompt Record → **AI Engine** (Sprint 3.3C: called automatically, via the Main Analysis Model Role, resolved to an exact AI Connection) → **AIRawResult** (persisted, multiple attempts traceable) → **AI Response Parser** (Sprint 3.2C, called automatically on the raw result) → **AIResponseRecord** (only created if validation passes) → **Strategy** (Sprint 3.3A's real render, auto-navigated to only after a valid record exists). A failure at any AI/Parser step cancels the Analysis with a readable message and never opens Strategy. **Execution** and **Learning** remain unwired to real Strategy data.

# Frozen Product Principles

Active decisions only — no historical discussion, no implementation detail (see the relevant SPEC or `product-docs/PRODUCT_STATUS.md` for those).

- Dashboard is a pure, independent real-time monitor — no AI, no strategy, raw data only.
- Research only configures inputs (source weights + additional evidence); it does not analyze.
- AI output appears only in Strategy.
- A data source with weight = 0 is excluded from collection and from the Analysis Payload entirely.
- Every Analysis Run collects fresh data only, after the user clicks Run Analysis — Dashboard's cache is never reused as Analysis data.
- If any required source fails, the whole Analysis cancels — no Payload, no Prompt Record, no silent fallback to cache.
- Every successful Analysis freezes exactly one immutable Snapshot, which becomes one Analysis Payload and one Prompt Record, both traceable by `analysisId`.
- Execution always separates the AI recommendation from the human decision, and only ever proceeds after explicit user confirmation.
- Trade Detail is read-only, immutable history — nothing is ever regenerated.
- All weights (data sources + additional evidence) must sum to 100%.
