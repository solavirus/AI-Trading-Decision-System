Version: 1.1.0

Status: Frozen

Last Updated: 2026-08

Revision note (1.1.0, 2026-08, Sprint 3.3B — implementation-blocking addition): added optional `AdditionalEvidenceItem.parsedContent`, populated only for image evidence that the new Image Evidence Parser successfully structured before Payload creation. This is additive and backward-compatible — every existing required field is unchanged, and a Payload built before this revision (with no `parsedContent` anywhere) remains fully valid under this schema. Made because Sprint 3.3B's task explicitly requires "the final payload must contain both: original evidence identity/metadata, parsed structured content" — impossible to satisfy without this field, so this is the "implementation-blocking contradiction" that sprint's documentation instructions anticipated. Does not touch the `payloadVersion` vs `version` field-naming discrepancy noted below, which remains separately deferred.

Addendum (Sprint 3.3B.2): `parsedContent`'s own internal shape (owned by `pipeline/src/ai/evidenceParser.ts`'s `ParsedImageEvidence`, not restated here — this spec treats it as one opaque structured object) gained `source`/`context` sub-fields for social-media screenshots (Product Decision 4: who appears to have published the information is part of the evidence). This is a change inside the already-opaque `parsedContent` value, not to the Payload's own field set — no `payloadVersion` bump, since nothing this document actually specifies (the presence and optionality of the `parsedContent` field itself) changed.

## Purpose

Defines the Analysis Payload — the single immutable object Research produces when the user submits an experiment configuration, and the contract every downstream stage (Prompt Builder, AI Engine, Strategy, Execution, Trade Detail) must trace back to via `analysisId`.

## When To Read

Read this document when:
- Changing what data Research collects or how it's structured into a Payload
- Adding a field consumed by Prompt Builder or a later stage
- Checking what `buildAnalysisPayload()` guarantees

Do NOT read this document when:
- Working on Dashboard cards or data collection mechanics (see `DATA_SOURCE_SPEC.md`)
- Formatting the Payload into a prompt string (see `PROMPT_BUILDER_SPEC.md`)

# Goal

Define the Analysis Payload.

The Analysis Payload is the single immutable object Research produces when the user submits an experiment configuration.

It is the boundary between configured input and everything downstream.

Prompt Builder, AI Engine, Strategy, Execution, and Trade Detail must all trace back to this object through `analysisId`.

Location

It does NOT redesign it.

# Principles

Research creates the Analysis Payload.

Research does NOT call an AI model.

Research does NOT modify the Payload after creation.

Dashboard refreshes must NOT modify an existing Payload.

Every submission creates a new Payload with a new `analysisId`.

No submission ever overwrites a previous Payload.

---

# Root Structure

```ts
type AnalysisPayload = {
  analysisId: string;
  createdAt: string;
  payloadVersion: string;

  symbol: string;
  timeframe: string;
  dateRange: string;

  sourceWeights: Record<string, number>;
  additionalEvidence: AdditionalEvidenceItem[];
  sourceSnapshots: ResearchSourceSummary[];
  selectedNewsEvents: SelectedNewsEvent[];

  dataQuality: DataQuality;
}
```

---

# Field Naming Note — `payloadVersion` vs `version`

The canonical specification field name is `payloadVersion`.

The current implementation names this field `version`.

The current implementation stores a bare integer (`1`).

The canonical specification defines this field as a semver-style string (e.g. `"1.0.0"`), for consistency with `promptVersion` and `responseVersion` in the sibling specifications.

This is two discrepancies, not one: the field name and the field type both differ from the code today.

Both will be migrated during a later implementation sprint (Prompt Builder or Sprint 3.1B).

Code is NOT modified by this specification.

# Field Definitions

## analysisId

Type

`string`

Required.

Generated by Research at Payload creation time.

Globally unique per submission (current implementation: timestamp + random suffix, uppercase-encoded).

This is the single identifier every downstream record (Prompt Record, AI Response Record, and eventually Trade Detail's historical view) must carry to remain traceable back to this Payload.

## createdAt

Type

`string` (ISO 8601)

Required.

Real wall-clock time at submission.

Must NOT use any fixed/mock "current time" value — the Payload always reflects the actual moment of submission.

## payloadVersion

Type

`string`

Required.

See Field Naming Note above.

## symbol

Type

`string`

Required.

The full trading pair as configured in Research (e.g. `"BTC/USDT"`).

## timeframe

Type

`string`

Required.

One of the values Research's timeframe selector currently offers (`"1H" | "4H" | "1D" | "1W"`).

## dateRange

Type

`string`

Required.

One of the values Research's date-range selector currently offers (e.g. `"最近7天"`).

This is a UI-label string today, not a normalized enum or a millisecond duration — noted as a possible future normalization, not something this specification changes now.

## sourceWeights

Type

`Record<string, number>`

Required.

Keys are the 11 Dashboard source keys (Market/Technical/Macro/News/ETF/On-chain/Sentiment/Derivatives/Stablecoin/Liquidation/Options — the same keys `DASHBOARD_SOURCES` and `WEIGHT_DEFS` share in lockstep).

Values are 0–100.

Per the frozen Weight Rules (`MVP Handbook.md`): the sum of every `sourceWeights` value plus every `additionalEvidence[].weight` value must equal 100 at submission time.

## additionalEvidence

Type

`AdditionalEvidenceItem[]`

Required (may be an empty array).

```ts
type AdditionalEvidenceItem = {
  id: string;
  type: string;
  title?: string;
  content?: string;
  reference?: string;
  weight: number;
}
```

`type` is the evidence category as configured in Research (e.g. `"截图" | "新闻" | "推文" | "观点" | "PDF"`).

`reference` holds a file name when the evidence is a file-backed type; otherwise omitted.

Raw file data (e.g. base64 image content) is deliberately NOT included in the Payload — only a reference, to keep the Payload small and because the Prompt Builder has no use for binary content.

## sourceSnapshots

Type

`ResearchSourceSummary[]`

Required.

Always exactly 11 entries — one per Dashboard source, produced by `getResearchSourceSummaries()` (Sprint 2.1) at the moment of submission.

```ts
type ResearchSourceSummary = {
  id: string;
  name: string;
  status: "loading" | "available" | "partial" | "unavailable" | "stale";
  updatedAt: string | null;
  values: Array<{ label: string; value: string | number; unit?: string }>;
  summary?: string;
  detailRoute?: string | null;
  error?: string | null;
}
```

This array is a deep copy, not a live reference — see Immutability Rules below.

## selectedNewsEvents

Type

`SelectedNewsEvent[]`

Required (may be an empty array).

0 to 10 entries, produced by the News Pipeline (`runNewsPipeline()`, Sprint 2.2) at the moment of submission.

```ts
type SelectedNewsEvent = {
  id: string;
  title: string;
  summary: string;
  category?: string;
  publishedAt: string | null;
  sourceCount: number;
  sources: string[];
  importanceScore: number;
  relatedAssets: string[];
  sourceArticleIds?: string[];
}
```

`sources` is capped at 5 display names; `sourceCount` reflects the true total.

`relatedAssets` is single-asset-scoped in the current implementation (always `[baseSymbol]` of the Payload's own `symbol`) — documented as a known limitation, not redesigned here.

## dataQuality

Type

`DataQuality`

Required.

```ts
type DataQuality = {
  unavailableSources: string[];
  partialSources: string[];
  staleSources: string[];
}
```

Each array holds `ResearchSourceSummary.id` values, derived directly from `sourceSnapshots` at submission time.

`dataQuality` remains part of the Analysis Payload — see AI_RESPONSE_SPEC.md's updated Missing Data section for how (and how much of) it should be surfaced downstream.

# Immutability Rules

A Payload's fields never change after creation.

`sourceSnapshots` is a deep copy (JSON round-trip) taken at submission time — a later Dashboard refresh, or any subsequent mutation of live `Store` state, must never alter an already-created Payload.

Every retrieval (`getAnalysisPayload(analysisId)`) returns a value freshly deserialized from persisted storage, not a shared in-memory reference — mutating a retrieved object in application code does not persist back to storage, by construction.

There is no update/patch operation for an existing Payload. None is planned.

A retry, a re-submission, or a correction always produces a new Payload with a new `analysisId`. Historical Payloads are never deleted or overwritten by a later submission.

---

# Creation Ownership

Research is the only module that creates an Analysis Payload.

Creation happens synchronously at the moment the user submits the experiment configuration (the "开始 AI 分析" action).

No other page, module, or background process creates, edits, or deletes an Analysis Payload.

Research does not call an AI model as part of, or after, Payload creation.

---

# Persistence Rules

Analysis Payloads are persisted in `localStorage` for the current MVP.

Storage key: `qa_analysis_payloads`.

Shape: a single JSON object mapping `analysisId → AnalysisPayload`.

No database is used for this record type in the current MVP, consistent with `MVP Handbook.md`'s prototype-stage scope.

---

# Retrieval by analysisId

`getAnalysisPayload(analysisId): AnalysisPayload | null`

Returns the exact Payload created at submission time, or `null` if the id does not exist.

This is the only retrieval contract. There is no query-by-symbol, query-by-date, or list-all contract defined at this time — Trade List / Trade Detail's eventual need to look up a Payload by `analysisId` (once a trade record stores that id) is expected to use this same function.

# Compatibility and Versioning

`payloadVersion` evolves independently of `promptVersion` and `responseVersion`, per the versioning principle already established in `PROMPT_BUILDER_SPEC.md`.

The schema in this document is `payloadVersion "1.0.0"`.

A breaking change to this schema requires a new `payloadVersion` and a recorded Product Decision in `product-docs/PRODUCT_STATUS.md`, per the Frozen UI Rule already governing this project's documentation system.

---

# Traceability Requirements

Every downstream record — Prompt Record, AI Response Record, and eventually any Trade record referencing this analysis — must carry the same `analysisId` as this Payload.

## Evidence ID stability (within one Payload)

Every id referenced inside a Payload — `additionalEvidence[].id`, `sourceSnapshots[].id`, `selectedNewsEvents[].id` and `selectedNewsEvents[].sourceArticleIds` — is guaranteed stable and dereferenceable for the lifetime of that one Payload, identified by its `analysisId`.

These ids are NOT guaranteed stable across different Payloads. In particular, `selectedNewsEvents[].id` originates from the news backend's per-request event ids, which are not stable across separate fetches — the same real-world news story may carry a different id in a Payload created five minutes later. This is a known characteristic of the current news pipeline, not a defect in this specification.

Cross-payload global ids are NOT required for MVP v1.

Traceability is guaranteed within one immutable analysis record identified by `analysisId` — not across records.

# Relationship to Prompt Record and AI Response Record

The Analysis Payload is the first of three linked, immutable records that together make up one full analysis:

Analysis Payload (this document)

↓ (same `analysisId`)

Prompt Record (`PROMPT_BUILDER_SPEC.md`)

↓ (same `analysisId`)

AI Response Record (`AI_RESPONSE_SPEC.md`)

All three are persisted independently, all three are linked by the same `analysisId`, and all three are immutable once created. See `PROMPT_BUILDER_SPEC.md` and `AI_RESPONSE_SPEC.md` for the other two records' own field definitions.
