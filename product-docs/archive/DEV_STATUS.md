Sprint 3.1B.1 added the first Settings page (`Settings → AI Connections`) so this no longer requires editing `.env` by hand: each of the 5 providers can now be enabled/disabled, given a base URL/API Key/default model, and test-connected from the UI, backed by a new JSON-file config store (`pipeline/data/ai_provider_config.json`, gitignored) that layers on top of (and overrides) the existing env-var configuration — this sprint is configuration-surface only, it does not touch prompt building, Strategy generation, or AI response parsing/viewing. Sprint 3.1B.2 improved the quality/size of what actually reaches the AI without touching the AI Engine, response parsing, Strategy, Execution, or Learning: Research now starts with zero Additional Evidence blocks (previously seeded 4 fake ones, including a title claiming a specific screenshot's content that was never real) and supports click/drag-drop/paste uploads across image/PDF/TXT/Markdown with file-kind auto-detection and no auto-generated titles; the Prompt Builder's `sourceSnapshots.news` no longer duplicates every fetched headline that `selectedNewsEvents` already carries in full (now 4 fixed summary counts instead of one row per article); and `market`/`technical`/`derivatives` — the 3 snapshots structured one row per tracked symbol — are now filtered to just the selected asset instead of listing all 6. Measured on a real submission (BTC/USDT, real backend data): promptText dropped from 21,762 to 13,905 characters (−36.1%); news snapshot rows from 64 to 4; market/technical/derivatives rows from 6 to 1 each; `selectedNewsEvents` itself confirmed byte-identical to an unfiltered pipeline run. Response parsing/validation against `AI_RESPONSE_SPEC.md` and Strategy integration do not exist yet — Strategy generation remains untouched, a deterministic pseudo-random mock (`signalFor()`/`signalForText()`) by explicit sprint scope. All trade/draft/payload/prompt/raw-AI-result state persists only to browser `localStorage`, not a backend database (the new AI Engine backend route itself is stateless — persistence of its results is a frontend concern, same pattern as everything else in this prototype). The complete user workflow (create a trade experiment → generate a strategy → execute → view in trade list/detail) is implemented and navigable; the incomplete part is that nothing after the raw AI response is backed by a validated response or wired into Strategy.

**2026-08-07 — Analysis Snapshot Integrity, a Frozen Product Decision** (recorded in full in `product-docs/PRODUCT_STATUS.md`): every AI analysis must be built only from data collected fresh, after the user clicks Run Analysis — never reused from Dashboard's already-loaded cache, never backfilled with stale data if a required source fails. Documented same-day as a gap (`buildAnalysisPayload()` read Dashboard's cache); Sprint 3.2A (same day) built a UI-only visual mock of the intended lifecycle with no real collection behind it; **Sprint 3.2B (2026-08-08) implements it for real** — see below. This is no longer an open gap.

**Sprint 3.2B, Analysis Runner Logic (2026-08-08)**: replaces Sprint 3.2A's scripted mock with the real Analysis Snapshot Integrity lifecycle. On Run Analysis, every data source with configured `weight > 0` (and only those — weight=0 sources are never fetched) is collected concurrently via a real `GET /api/sources/:key?fresh=1` request, each independently timed out (`ANALYSIS_SOURCE_TIMEOUT_MS`, one named constant, real AbortController per source) and independently validated (HTTP ok + well-formed `SourceResult` shape + backend didn't report `status:'error'`; empty content — 0 news events, 0 liquidations — is explicitly NOT a failure, matching the decision's Validation Rules exactly). Additional Evidence gets its own MVP-level check (every file-type item must actually have an uploaded file; no OCR/parsing). If anything required fails, the whole analysis cancels — no Payload, no Prompt Record — and the existing failure UI now lists every source that failed, not just one (collection is concurrent, so multiple can fail together). Only once everything required succeeds does the snapshot freeze and feed into `buildAnalysisPayload()`/`buildPromptRecord()` — the same two functions as every prior sprint, changed only in what feeds them (real, just-collected data, converted by a new `freshSourceResultToSnapshot()`, never `Store.live`). Stops after the Prompt Record is built — still no AI call (Sprint 3.2C's job) — and, unlike 3.2A's mock, no longer auto-navigates to Strategy (wiring a real Prompt into the still-100%-mock Strategy page would misrepresent them as connected). A new dev-only Diagnostics toggle (replacing 3.2A's success/failure/slow scripted-outcome picker, which stopped meaning anything once collection became real) shows collected/skipped/failed source counts, collection duration, Payload/Prompt sizes, and Prompt build duration — all real numbers from the actual run, no token estimation. `getResearchSourceSummaries()`/`researchSourceSummaryFor()` (the Dashboard-cache adapter this replaces) are deleted, fully unused now. Backend: one small, backward-compatible change — `GET /api/sources/:key` gained an opt-in `?fresh=1` that bypasses the existing 20s cache read (omitting it changes nothing for any existing caller, including Dashboard's own polling).
